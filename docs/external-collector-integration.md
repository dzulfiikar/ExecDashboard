# External Collector Integration

This guide explains how to feed Hygieia Executive Dashboard metrics from an external collector written in Node.js, Go, Python, or another runtime. Use this when a data source is easier to poll outside the legacy Java/Spark `exec-analysis` module.

## Integration Options

| Option | Best for | Tradeoffs |
| --- | --- | --- |
| Direct MongoDB writer | Independent Node.js, Go, Python, or cron-based collectors. | Fastest path, but you must preserve collection schemas and indexes yourself. |
| Java collector inside `exec-analysis` | Collectors that should share existing scheduling, Spark processing, and repository code. | Requires Java 8 and changes to the legacy backend. |
| Staging collection plus Java rollup | External technology gathers raw data, Java analysis converts it into dashboard rollups. | More moving parts, but keeps dashboard write logic in Java. |

For non-Java technologies, prefer the staging or direct-writer patterns. Do not make external collectors call internal Java classes; write to MongoDB through a stable document contract.

## What The Dashboard Reads

The API primarily reads derived executive collections, not arbitrary source data. External collectors should either populate these collections directly or populate staging collections that an analysis process converts later.

Important target collections:

- `collectors` - one document per collector instance/type.
- `collector_items` - one document per external tool scope, such as repository, service, job, project, or application.
- `collector_status` and `collector_updated_details` - collector health and last update metadata.
- `metrics_detail` - API-facing metric summary and time-series data by portfolio, product, or component.
- `building_blocks` - product/component cards and metric summaries displayed by dashboard views.
- Metric-specific collections such as `commits`, `builds`, `deployments`, `service_now_issues`, or custom staging collections when you need raw event history.

## Required Identity Mapping

Before writing metrics, decide how external data maps to Executive Dashboard hierarchy:

| External concept | Dashboard field |
| --- | --- |
| Portfolio or executive owner | `MetricLevel.PORTFOLIO`, `metricLevelId` usually an executive or portfolio id. |
| Product, application, or service | `MetricLevel.PRODUCT`, `metricLevelId` usually an app/product id. |
| Component, repository, job, or deployable unit | `MetricLevel.COMPONENT`, often represented through `building_blocks`. |
| Metric category | `MetricType` enum value and route name. |
| Line of business | `lob`. |

Use existing identifiers where possible. If the UI route or API query expects portfolio/product ids generated by `PortfolioCollector`, external collectors must write data against those ids or update the hierarchy first.

## Supported Metric Types

Metric route names are defined in `MetricType.java`, for example:

- `open-source`
- `security-violations`
- `test-automation`
- `static-code-analysis`
- `production-incidents`
- `unit-test-coverage`
- `production-releases`
- `pipeline-lead-time`
- `scm-commits`
- `traceability`
- `performance-test`
- `engineering-maturity`

If you need a brand-new metric type, Java changes are required in `exec-core` and likely `exec-api`/`exec-ui`. For an external-only integration without Java changes, map the source data to an existing `MetricType`.

## Direct MongoDB Writer Contract

A direct external collector should follow this flow:

1. Connect to MongoDB using environment-specific credentials.
2. Upsert one `collectors` document for the external collector.
3. Upsert one or more `collector_items` documents for each external data scope.
4. Write raw events to a source or staging collection if historical traceability is needed.
5. Upsert `metrics_detail` documents for API-facing summaries and time series.
6. Update `building_blocks` when product/component cards need current summary counts.
7. Update collector status and last-updated metadata.

Use idempotent upserts keyed by stable business identifiers. Avoid blind inserts that create duplicate metric rows on every run.

## `metrics_detail` Shape

The Java model `MetricsDetail` maps to the `metrics_detail` collection. A practical JSON shape is:

```json
{
  "metricLevelId": "APP123",
  "name": "Payments API",
  "lob": "Retail",
  "level": "PRODUCT",
  "type": "SCM_COMMITS",
  "summary": {
    "name": "scm-commits",
    "lastScanned": { "$date": "2026-05-28T00:00:00Z" },
    "lastUpdated": { "$date": "2026-05-28T00:05:00Z" },
    "trendSlope": 0,
    "totalComponents": 1,
    "reportingComponents": 1,
    "dataAvailable": true,
    "counts": [
      {
        "label": { "type": "commits" },
        "value": 42
      }
    ]
  },
  "timeSeries": [
    {
      "timestamp": 1716854400000,
      "counts": [
        {
          "label": { "type": "commits" },

        }
      ]
    }
  ],
  "totalComponents": 1,
  "reportingComponents": 1,
  "processed": true

```

Validate field names against the Java models before production use. The dashboard code expects Java enum names for persisted enum fields, while API routes use the route names from `MetricType.getName()`.

## Node.js Collector Skeleton

```javascript
const { MongoClient } = require('mongodb');

const uri = process.env.MONGO_URI;
const dbName = process.env.MONGO_DB || 'analyticsdb';

async function run() {
  const client = new MongoClient(uri, { useUnifiedTopology: true });
  await client.connect();
  const db = client.db(dbName);
  const now = new Date();

  const collectorResult = await db.collection('collectors').findOneAndUpdate(
    { name: 'nodejs-example-collector' },
    {
      $set: {
        name: 'nodejs-example-collector',
        collectorType: 'SCM',
        enabled: true,
        online: true,
        lastExecuted: now.getTime()
      }
    },
    { upsert: true, returnDocument: 'after' }
  );

  await db.collection('collector_items').updateOne(
    { collectorId: collectorResult.value._id, description: 'payments-api' },
    {
      $set: {
        description: 'payments-api',
        niceName: 'Payments API',
        enabled: true,
        pushed: true,
        collectorId: collectorResult.value._id,
        lastUpdated: now.getTime(),
        options: { repoUrl: 'https://example.invalid/payments-api.git', appId: 'APP123' }
      }
    },
    { upsert: true }
  );

  await db.collection('metrics_detail').updateOne(
    { metricLevelId: 'APP123', level: 'PRODUCT', type: 'SCM_COMMITS' },
    {
      $set: {
        metricLevelId: 'APP123',
        name: 'Payments API',
        lob: 'Retail',
        level: 'PRODUCT',
        type: 'SCM_COMMITS',
        summary: {
          name: 'scm-commits',
          lastScanned: now,
          lastUpdated: now,
          trendSlope: 0,
          totalComponents: 1,
          reportingComponents: 1,
          dataAvailable: true,
          counts: [{ label: { type: 'commits' }, value: 42 }]
        },
        timeSeries: [{ timestamp: now.getTime(), counts: [{ label: { type: 'commits' }, value: 42 }] }],
        totalComponents: 1,
        reportingComponents: 1,
        processed: true
      }
    },
    { upsert: true }
  );

  await client.close();
}

run().catch((error) => {
  console.error(error);
  process.exit(1);
});
```

## Go Collector Skeleton

```go
package main

import (
    "context"
    "os"
    "time"

    "go.mongodb.org/mongo-driver/bson"
    "go.mongodb.org/mongo-driver/mongo"
    "go.mongodb.org/mongo-driver/mongo/options"
)

func main() {
    ctx := context.Background()
    uri := os.Getenv("MONGO_URI")
    dbName := os.Getenv("MONGO_DB")
    if dbName == "" {
        dbName = "analyticsdb"
    }

    client, err := mongo.Connect(ctx, options.Client().ApplyURI(uri))
    if err != nil {
        panic(err)
    }
    defer client.Disconnect(ctx)

    db := client.Database(dbName)
    now := time.Now().UTC()

    _, err = db.Collection("metrics_detail").UpdateOne(
        ctx,
        bson.M{"metricLevelId": "APP123", "level": "PRODUCT", "type": "SCM_COMMITS"},
        bson.M{"$set": bson.M{
            "metricLevelId": "APP123",
            "name":          "Payments API",
            "lob":           "Retail",
            "level":         "PRODUCT",
            "type":          "SCM_COMMITS",
            "summary": bson.M{
                "name":                "scm-commits",
                "lastScanned":         now,
                "lastUpdated":         now,
                "trendSlope":          0,
                "totalComponents":     1,
                "reportingComponents": 1,
                "dataAvailable":       true,
                "counts": []bson.M{{
                    "label": bson.M{"type": "commits"},
                    "value": 42,
                }},
            },
            "timeSeries": []bson.M{{
                "timestamp": now.UnixMilli(),
                "counts": []bson.M{{
                    "label": bson.M{"type": "commits"},
                    "value": 42,
                }},
            }},
            "totalComponents":     1,
            "reportingComponents": 1,
            "processed":           true,
        }},
        options.Update().SetUpsert(true),
    )
    if err != nil {
        panic(err)
    }
}
```

## Staging Collection Pattern

Use a staging collection when external payloads do not match dashboard models yet. Example collections:

- `external_nodejs_metrics`
- `external_go_metrics`
- `external_security_findings`

Recommended staging fields:

```json
{
  "source": "github-actions",
  "collector": "nodejs-example-collector",
  "appId": "APP123",
  "componentId": "payments-api",
  "metricType": "scm-commits",
  "observedAt": { "$date": "2026-05-28T00:00:00Z" },
  "value": 42,
  "dimensions": {
    "branch": "main",
    "repo": "payments-api"
  },
  "raw": {}
}
```

Then add or schedule Java analysis logic to convert staging records into `metrics_detail` and `building_blocks`. This keeps UI-facing document generation inside the existing Java model layer.

## Scheduling And Deployment

External collectors can run as:

- Cron jobs.
- Kubernetes CronJobs.
- Docker Compose sidecars.
- CI/CD scheduled jobs.
- Serverless scheduled functions, if they can securely reach MongoDB.

Operational requirements:

- Use one writer per metric/id combination, or coordinate writes with deterministic upsert filters.
- Set timeouts for external API calls.
- Record last successful execution and failure details.
- Emit logs with collector name, source, item count, and write count.
- Keep MongoDB credentials in environment variables or secret mounts, not in source code.

## Validation Checklist

- The target portfolio/product/component id already exists or is intentionally created by the collector.
- `MetricType` and `MetricLevel` values match Java enums.
- Documents are upserted, not duplicated.
- Dates are stored as BSON dates where Java expects `Date`, and epoch milliseconds where Java models use `long` timestamps.
- `metrics_detail.metricLevelId` has an index and is present on every dashboard-facing metric document.
- API endpoints under `/api/metrics/...` return the expected summary/detail after the collector writes.
- UI cards render the metric or fail gracefully if the card is not configured.

## When Java Changes Are Required

External collectors alone are not enough when you need:

- A brand-new `MetricType` enum value.
- New API routes or service behavior.
- New UI cards, labels, or visualizations.
- New repository queries or indexes.
- Complex rollups that must be shared with existing Java collectors.

In those cases, update `exec-core`, `exec-api`, `exec-analysis`, and `exec-ui` together and document the new collection contract.
